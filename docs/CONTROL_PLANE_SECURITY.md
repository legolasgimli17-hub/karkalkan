# Control-Plane Security Checklist

Last reviewed: 2026-08-18

This checklist covers the accounts that can change source code, deployments, databases, monitoring, payments or marketplace access. Application code cannot safely enable account-owner MFA on someone else's behalf because enrollment requires the owner to prove possession of an authenticator and retain recovery material.

## Required before production handover

For GitHub, Vercel, Supabase and Sentry:

1. Use a named owner account with a unique password generated by a password manager.
2. Enable authenticator-app or hardware-key MFA. Avoid SMS as the only factor where a stronger option is available.
3. Save recovery codes outside the repository and outside the same device/account used for MFA.
4. Remove unused organization members, stale OAuth apps, deploy keys, personal access tokens and sessions.
5. Give day-to-day collaborators the least privileged role; keep the number of organization owners minimal.
6. Enable security alerts for new sign-ins, membership changes, secret changes and production deployments where the provider supports them.

For Paddle, Amazon and FLO:

1. The legal/authorized business owner must create or approve the account and complete any identity, business, domain or payout verification.
2. Enable the strongest MFA offered by the provider before storing live credentials.
3. Create KârKalkan-specific API credentials rather than reusing a personal password or another integrator's key.
4. Enter secrets only in the provider's dashboard or KârKalkan's authenticated credential form. Never paste them into chat, GitHub, support tickets or documentation.
5. Record the owner, creation date, scope and rotation date without recording the secret value.

## Supabase authentication state

The current Supabase organization is on the Free plan. Supabase's built-in leaked-password-protection switch is therefore unavailable. Normal KârKalkan signup applies a 12-character mixed-class policy and checks the password against Have I Been Pwned using the k-anonymity range protocol; only the first five SHA-1 hash characters leave the browser. This is an application-layer safeguard, not a claim that the Supabase Pro feature is enabled.

If the project is upgraded to a plan that offers leaked-password protection, the owner should enable it in **Authentication → Providers → Email** and keep the application-layer check as defense in depth.

## Rotation after a transfer or suspected exposure

Rotate, in this order, GitHub tokens/deploy keys, Vercel tokens, Supabase secret keys and database password/pooler URL, Sentry DSN if abused, Paddle API/webhook secrets, Amazon LWA credentials, and marketplace credentials. Update only the relevant server-side secret stores, deploy once, verify safe service health, then revoke the previous credential. Never rotate through committed `.env` files.

## Evidence to retain

Retain a dated checklist showing MFA enabled, recovery ownership confirmed, stale access removed and credentials rotated. Do not attach screenshots containing QR codes, OTPs, recovery codes, API secrets, database URLs or marketplace credentials.
